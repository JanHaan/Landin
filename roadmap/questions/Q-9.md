# Q-9 — Which commands leave `refine`, and do they link its library in lockstep?

Asked by R18.10 on 2026-11-18.

R18 makes `refine` a dispatcher: a command stays built in, or becomes its
own executable `refine-NAME` that `refine NAME` runs. The command
inventory, `roadmap/inputs/command-inventory.md`, counts thirteen commands
and proposes a classification; its first question asks whether a shipped
split command links the same Ada library as `refine`, built and released
with it, so that no stable interface between them is needed. Both are the
shape of the tool its users see, and so yours. `lsp` and the new `dap` are
Q-10's.

| Command | Proposed | Why |
| --- | --- | --- |
| `check`, `compile`, `run` | built in | one body, `Driver.Execute`; the compiler itself |
| `fmt` | built in | named core by you; small once R18.20 cuts the loading edge |
| `explain` | built in | the diagnostics' own documentation; knows every shipped code |
| `version`, `help`, `completion`, `targets` | built in | small; they describe the installation and list the split commands too |
| `svd` | split | a generator with 1.0 MB of its own release text, device inputs and its own tests; no front end |
| `bindings` | split | runs Clang (D821); 1.8 MB of its own text; no front end |
| `site` | split | a debugging aid beside `dap`; nine units, reads a map file |

In lockstep, `refine-svd` of one release is never run by another release's
`refine`, so the two share Ada types and the catalogue and nothing between
them is versioned. A tool contributed from outside, in any language, would
need a stable interface; the JSON `refine` already prints (diagnostics,
`version --json`, the source maps) is where one would start, and Q-12 says
what such a tool is held to.

**Options:**

1. The classification above, and every shipped split command links the
   compiler's library in lockstep: built from the same tree, released in
   the same archive and flake, with no interface of its own.
2. The same classification, but each split command talks to `refine`
   only through its JSON outputs, a versioned interface from the start.
3. Keep every existing command built in; only new commands, `dap` first,
   are split, and R18.70 is dropped.

**Recommendation:** option 1. It keeps one catalogue, one warning policy and
one release, and splitting saves `refine` the 2.8 MB of `svd` and
`bindings` code, which no compile uses. A stable interface waits for the
first contributed tool that needs one.

**Default until answered:** `check`, `compile`, `run`, `fmt`, `explain`,
`version`, `help`, `completion` and `targets` stay built in; `svd`,
`bindings` and `site` become `refine-svd`, `refine-bindings` and
`refine-site`, linked in lockstep with the compiler's library and shipped
in its archive and flake.

**What waits on the answer:** R18.10's close, whose exit evidence is the
decision in `spec.md`; R18.70, written to this default, and the shipping
half of R18.50.
