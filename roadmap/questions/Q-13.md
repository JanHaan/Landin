# Q-13 — Is cutting the `Driver.Library` to `Driver.Loading` edge R18's first step?

Asked by R18.10 on 2026-11-18.

The command inventory's eighth question. `Driver.Library`'s body withs
`Driver.Loading` for one path helper, which links the whole front end, 30
units and 5.9 MB of release text, into everything that withs
`Driver.Library`. The inventory measured what that costs `fmt`, `explain`
and `version` as closures of their own: 6.8 MB for `explain` where 0.5 MB
would do, 0.6 MB for `version`, 1.9 MB for `fmt`. The order of R18's work is
yours.

R18.10 found what the inventory does not say. Under Q-9's default those
three stay inside `refine`, which links the whole compiler anyway, so the
cut shrinks no executable shipped today. It matters for a split command
that withs `Driver.Library`: `Landin.Source_Maps` does, and a split `dap`
(Q-10's default) reads source maps, so `refine-dap` would carry the front
end through this one edge.

**Options:**

1. R18.20 cuts the edge first, as R18 is written, and measures the three
   closures before and after.
2. Fold the cut into R18.60, `dap`, the first split command that withs
   `Driver.Library`, and measure `refine-dap` itself; R18.20 is retired.
3. Do not cut it.

**Recommendation:** option 1, with R18.20's exit evidence adding
`Source_Maps`' closure to the three. The change is small and mechanical,
it is done before anything depends on the edge, and every later split
measures against the smaller graph. Option 2 is as good if `dap` is built
in after all (Q-10), since nothing shipped then gains.

**Default until answered:** R18.20 cuts the edge as R18's first item after
this one, as R18 is written.

**What waits on the answer:** R18.10's close, and R18.20's place in R18.

**Answer (2026-11-18, the maintainer):** option 1: R18.20 cuts the edge
first, and its exit evidence also measures `Landin.Source_Maps`' closure.
Recorded as D1386. Closed.
