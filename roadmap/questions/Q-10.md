# Q-10 — Is `lsp` built in or split, and is the new `dap`?

Asked by R18.10 on 2026-11-18.

The command inventory's sixth question asks whether `lsp` stays in
`refine`, and R18.10's text adds whether R18.60's Debug Adapter Protocol
server, `dap`, is built in or external. R18.60 says "built in unless R18.10
finds external the better fit"; the inventory proposes it split. Both are
what editors launch, so where they live is yours.

`lsp` links every backend and IR pass, because `Server.Analysis` uses
`Driver.Checking`, which runs the backend for the handler-fit check (D572).
A `refine-lsp` would carry the compiler a second time, about 18.6 MB of
release text, and save `refine` nothing. Editors start it as
`refine lsp`, which the dispatcher would keep working either way.

`dap` is a long-lived adapter that drives GDB and LLDB, the sessions the
targets already script, and needs the library only for the source maps and
the target facts. It is the first command that does not exist yet, so it
can be written to the split's rules from its first line. R18.60 already
depends on R18.50, the dispatcher.

**Options:**

1. `lsp` built in; `dap` split, as `refine-dap` in lockstep with the
   library and shipped in the archive, run as `refine dap`.
2. Both built in; R18.60 then needs only R18.10 and could come before the
   dispatcher.
3. Both split.

**Recommendation:** option 1. Splitting `lsp` duplicates the compiler for no
gain; `dap` uses little of it, keeps GDB and LLDB handling out of the
compiler's executable, and is the split's first new case.

**Default until answered:** `lsp` stays built in, and `dap` is a split
command, `refine-dap`, linked in lockstep and shipped in the archive and the
flake.

**What waits on the answer:** R18.10's close, and R18.60's text, which is
rewritten to the answer at that close.
