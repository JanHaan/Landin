# Q-12 — What is a contributed `refine-NAME` held to, and whose diagnostics does it emit?

Asked by R18.10 on 2026-11-18.

The command inventory's fourth and fifth questions. A command `refine`
ships is held to the strict requirements the inventory lists: every host
effect through `Landin.Platform` with fake-filesystem driver cases, the
black-box "destroys nothing it did not create" controls, declared and
staged inputs, catalogued `L` codes explained in `docs/diagnostics.md`,
deterministic output across hosts, the target matrix, mutation evidence
where the roadmap asks, and the pinned toolchain with warnings as errors. A
tool someone else writes, found on PATH (Q-11), cannot be held to the Ada
seam, the closed catalogue or the warning policy. What the project promises
about such tools is yours.

**Options:**

1. A contributed tool is released from every requirement. A tool shipped
   in the archive keeps the black-box "destroys nothing" and determinism
   controls, run in the gate, and every shipped split command keeps `L`
   codes in the one catalogue. A contributed tool uses a prefix of its own
   and answers `refine-NAME explain CODE`, to which `refine explain`
   forwards a code it does not know.
2. As option 1, but `refine explain` explains only `L` codes and forwards
   nothing.
3. Contributed tools are not supported: only shipped split commands are
   dispatched (Q-11's option 2).

**Recommendation:** option 1. The shipped commands lose nothing, the one
catalogue stays closed, and a contributed tool's codes are still one
`refine explain` away.

**Default until answered:** option 1: contributed tools are released from
every requirement and use their own code prefix, which `refine explain`
forwards to `refine-NAME explain`; shipped split commands keep `L` codes and
keep the destroys-nothing and determinism controls in the gate.

**What waits on the answer:** R18.10's close; R18.50's forwarding and
R18.70's controls, written to this default.
