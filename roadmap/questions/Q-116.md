# Q-116 — Does a static Linux archive replace the glibc archives, or sit beside them?

Asked by R23.40 on 2026-11-21.

R23.40 found that the pinned GNAT links `refine` statically against glibc
with no source change, and that the result passes the whole release test
program on Linux x86-64 and runs on Alpine, x86-64 and arm64, with no
C library of its own; `roadmap/inputs/static-linux-refine.md` has the
evidence. A musl build would need a GNAT toolchain nobody publishes, so
R23.50 is rewritten to publish the static glibc build. What the release
offers Linux users, and under which names, is the published shape of the
project, and so yours. The archive grows by about 4 %, and carries
glibc's licence, since glibc is linked into it.

**Options:**

1. The static archive replaces the glibc one under the same names,
   `landin-VERSION-x86_64-linux.tar.gz` and
   `landin-VERSION-aarch64-linux.tar.gz`: one Linux archive per
   architecture, which `install.sh`, the Homebrew formula, the flake's
   `refine-bin` and the user image keep taking, and `install.sh` stops
   refusing musl and NixOS hosts.
2. The static archive is published beside the glibc one, under a name of
   its own such as `landin-VERSION-x86_64-linux-static.tar.gz`, and
   `install.sh` takes it on a musl or NixOS host only.
3. No static archive: R23.50 is retired and the README keeps sending musl
   and NixOS users to nix or the source build.

**Recommendation:** option 1. The static archive runs everywhere the
dynamic one does, start-up is no slower, and two archives per architecture
would be two things to test, publish and explain for no user who needs the
dynamic one.

**Default until answered:** the static glibc archive replaces the glibc
archive under the same names for Linux x86-64 and arm64, and `install.sh`
takes it on every Linux host, musl and NixOS included.

**What waits on the answer:** R23.50's release and install-script half;
its build and gate job are the same under options 1 and 2.
