`item.py push` and `item.py promote` push through `origin`, whose second push URL is the git.sr.ht mirror, and treat the one command's failure as the whole push failing. R23.10 met it on 2026-11-21 when git.sr.ht refused every push ("Could not chdir to home directory /var/lib/git: Permission denied ... A temporary error has occured"): GitHub took the candidate and then `main`, but `push` recorded no runs, and `promote` said the push to main failed, gave up the promotion token while GitHub's `main` was already the candidate, and left the item unpromoted in its state, so `item.py gate --main` and `finish` refused. The item followed main's gate with `gate_watch.py` by hand. The documents say how a deletion reaches the mirror but not what to do when only the mirror refuses.

`scripts/item.py`'s promotion token and status say less than they do, as the items running on 2026-11-20 and 21 met them. `merge-main` on a branch that has already merged main once does not take the promotion token, so main can move under the last gate, which cost R16.23 two gate-and-boards rounds. An agent that is no item can read the token with `item.py queue` but cannot take it. `item.py status` showed finished boards dispatches as queued.

Completion: `push` and `promote` push to GitHub first and judge the step by it, then push the mirror and report a mirror failure as a mirror failure to retry, keeping the item's state promoted; `docs/process.md` says how to bring the mirror up to date afterwards; `merge-main` takes the token whenever it merges; a session that is no item can take and release the token; `status` shows a dispatch's state as GitHub gives it.
